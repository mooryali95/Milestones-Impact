## ١. كيف يعمل المالك (التزم به حرفيًا)

- **المنهج الدائم في `CLAUDE.md`**: أي اقتراح أو ملاحظة أو ميزة جديدة من المالك تمر بست خطوات: فهم، تحليل الأثر على القائم، مقارنة بأفضل الممارسات، تصور متكامل بخيارات وتوصية ومراحل، **لا بناء قبل اعتماده**، ثم إغلاق الحلقة (اختبارات، CI، إنتاج، تقرير صادق).
- **اللغة**: المالك يكتب بالعربية. الرد بالعربية، والنص الإنجليزي منفصل لا يتداخل.
- **مصدر واحد لكل معلومة**: لا تنسخ رقمًا أو نصًا بين ملفين؛ اقرأه من مصدره (`labels.js`، `logic.js`، الجداول).
- **الترقيم بالنسخ**: لا تحذف ملفًا قديمًا؛ أنشئ `v2`.
- **الإنتاج**: نظام الأمان الآلي يمنع SQL الإنتاج حتى يكتب المالك موافقة **تسمّي الترحيل نفسه**، بصيغة مثل:
  «طبّق ترحيل X على الإنتاج وادمج #N وانشر». عبارة «اعتمد» وحدها لا تكفي؛ اطلب الصيغة الصريحة.
- **الأسرار**: لا تكتب سرًا في ملف. لا تطلب من المالك لصق سر في المحادثة.

## ٢. دورة كل مرحلة (اتبعها كما هي)

1. فرع من `origin/main`، بناء، اختبارات وحدة جديدة للمنطق النقي.
2. الفحوص المحلية كلها:
   ```
   npm run lint
   npx vitest run                     # 504 اختبارًا الآن
   npx -y deno@2 check --node-modules-dir=auto supabase/functions/leaders-api/index.ts && rm -f deno.lock
   npm run leaders:build && npm run admin:build   # مخرجات leaders/ وadmin/ تُودع في Git
   npx playwright test                # 121 اختبارًا
   ```
3. دفع، فتح PR (بلا قالب في المستودع)، الاشتراك في نشاطه.
4. بعد موافقة المالك الصريحة: تطبيق الترحيل **قبل** نشر الدالة (الخادم يقرأ الأعمدة الجديدة):
   ```
   python3 -c "import json;print(json.dumps({'query':open('supabase/migrations/<file>.sql').read()}))" > /tmp/q.json
   curl -s -X POST https://api.supabase.com/v1/projects/eormhcupwgwpllhrfxxg/database/query \
     -H "Authorization: Bearer $SUPABASE_ACCESS_TOKEN" -H "Content-Type: application/json" -d @/tmp/q.json
   ```
   ثم استعلام تحقق بعده.
5. انتظار `build-and-test` أخضر (عبر `gh api repos/mooryali95/Milestones-Impact/commits/<sha>/check-runs`؛ استعلام GraphQL لـ`gh pr checks` محجوب).
6. دمج squash، إلغاء الاشتراك، ثم:
   ```
   git fetch origin main && git checkout -B main origin/main
   npx -y supabase@latest functions deploy leaders-api --project-ref eormhcupwgwpllhrfxxg --use-api
   ```
   تحقق: `POST .../functions/v1/leaders-api` بلا مصادقة يرد 401.
7. تقرير للمالك: ما بُني، ما تحقق منه فعلًا، ما **لم** يُجرَّب (لم نجرّب أي شاشة بحساب مسجّل؛ قل ذلك صراحة).

**تنبيه CI**: يعمل على `ubuntu-24.04` (Playwright لا يدعم 26.04)، وdeno بـ`--node-modules-dir=auto`. اختبار «نموذج التواصل» في `e2e/site.spec.js` بطيء أحيانًا في التشغيل الكامل وينجح منفردًا.
**اختبار المصدر الواحد** (`leaders-app/src/single-source.test.js`) يرفض أي لون hex في `admin-app/` و`leaders-app/` (استعمل متغيرات `--brand-*` و`--st-*`). مكوّن القاعة في `shared/hall/` خارج نطاقه عمدًا.

### خيوط مهمة يجب فهمها قبل التعديل
- **الرحلة تُحسب من مصدر واحد**: `participant.ts → journeyFor()` يبني الرحلة والمعالم والتقييم المستمر والتقييم الختامي المعتمد ومجموعة المشارك؛ ويستعمله المشارك والأدمن ومنسق الجهة.
- **القواعد الفارغة = السلوك الأصلي حرفيًا** (اختبار يثبته في `journey-rules.test.js`). لا تكسر هذا.
- **المستوى الموحد** في الدفعة المتجانسة يمر عبر `contentLevelsFor()` إلى: الرحلة، الكتيب (`approvedLevels`)، الأنشطة، النماذج، نماذج المبادرة. القياس والمسار والأولوية والتقرير من قياس المشارك دائمًا.
- **التقييم الختامي** لا يُخزَّن حيًا؛ يُحسب عند العرض، وتُحفظ `snapshot` لحظة الرفع للاعتماد. المكوّن الغائب لا يُحسب صفرًا.
- **كاتون**: المفتاح والشرح لا يُرسلان للمشارك قبل إتمام الموضوع، وتُقفل الإجابات بعده. في القاعة يُقفل ما كشفه الخبير، ويُقبل في النمط الحي الجملة المعروضة فقط (`hall.ts → hallGate`).
- **القاعة**: التزامن بسؤال خفيف عن `hall_sessions.version` (2 ث للعرض، 3 ث للجوال)، لأن الجداول مغلقة أمام anon. `hallView()` يقرر من يرى ماذا (لا اختيارات للزملاء قبل الكشف).

## ٥. المتبقي (بالترتيب المعتمد)

### المرحلة 8: طلبات الأقران وتأكيد الخبير (معتمدة التصور، لم تُبنَ)
**ما طلبه المالك**: يضع المشارك سؤالًا أو جزءًا من مشروعه، ويرفع «طلب توجيه»، فيظهر لأعضاء الدور المعني (فريق التوجيه أو الدعم)، فيجيبون أو يضعون تصورًا، ثم يأتي الخبير فيؤكّد الكلام. إدارة كاملة للخبير، واحترام اسم صاحب الإسهام، ونمط الإشراف لكل دفعة: أقران مع خبير، أو خبير فقط، أو مزيج.
**تصور مقترح للبناء**:
- جدول `peer_requests` (participant_id، cohort_id، source: sentence|milestone|capstone|free، ref_id، text، target_team، status: open|answered|confirmed|closed) و`peer_answers` (request_id، author_id، text، status: pending|confirmed|corrected|hidden، expert_note، confirmed_by).
- `cohorts.supervision`: peers_expert | expert_only | mixed (في expert_only يذهب الطلب للخبير مباشرة عبر `ChooseExpert` القائم).
- القائم الذي يُربط به: `cohort_roles` (الفريق)، `hall_presence.hand` (اليد المرفوعة تصير طلبًا)، خيارات كاتون «لدي سؤال/تحتاج بحث» (تقترح رفع طلب)، `ChooseExpert` (لا تكرار: مسار واحد بخيارين).
- المصدر السادس في التقييم المستمر: إسهام مؤكَّد (أضف `peer` في `CONTINUOUS_SOURCE_AR` و`continuousAssessment`).
- في المسار الذاتي للقاعة يظهر سجل النشاط (كما في نموذج التصميم).
- **الأسماء**: اسأل المالك هل يظهر اسم المجيب دائمًا أم يُخفى حتى التأكيد (سؤال مفتوح، لم يُجب).
- **الضوابط**: الإجابة غير المؤكدة تُعلَّم «بانتظار تأكيد الخبير»؛ إبلاغ وإخفاء بيد الخبير.

### المرحلة 9: ملف المشارك للخبير
صفحة واحدة تُقرأ في دقيقة: من هو (المستوى، نقاط القوة، المسار)، أين هو (المرحلة، المعالم، التأخر)، ما حدث (الجلسات والطلبات والملاحظات)، التقييم المستمر واتجاهه، الإجابات المعلّقة لتأكيده، وسطر «المطلوب منك الآن». **مهم**: اعتماد التقييم الختامي الآن من حسابات اللوحة فقط؛ إتاحته للخبير من بوابته (`ExpertPortal.jsx`، `xp.*` في `index.ts`) جزء من هذه المرحلة، مع قصر رؤيته على من يتابعهم.
