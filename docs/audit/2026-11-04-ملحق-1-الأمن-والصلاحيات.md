## HIGH

### H1. Client-supplied `ref` grants organization attribution → free paid entitlement + org tenancy pollution (and unlink never revokes)

**Evidence**
- `participant.ts:108-113` `resolveOrg(b)` → `orgByCode(b.org)` then `orgByHost(hostOf(b.ref))`. `b.ref` is a request-body field.
- `participant.ts:142-144` `sponsorFor()` = `sponsorByCode || resolveOrg(b) || orgByEmail(email)`; called at registration from `authStart` (`:186`, result stored in `pending_profile` and written to `participants.organization_id` at `:241-246`) and from `authGoogle` (`:268-274`).
- `participant.ts:90-101` `orgByHost` matches the host and every parent domain against `organizations.domains`.
- `payments.ts:31-35` `sponsorOf(p)` returns the org if `p.organization_id` points at an active org; `:56` `pinSponsor` inserts permanent `entitlements` rows (`source:'sponsor'`, `value_cents = contract_cents`) for `assessment` and `program` on the first `access()` call. `index.ts:310-311` gates every paid action on `access()`.
- `admin.ts:108-124` `assignOrg` (the admin "unlink/move" action) only updates `organization_id`/`org_via`; no code anywhere revokes `source='sponsor'` entitlements (grep confirms no `entitlements` reference in `admin.ts`/`sponsor.ts`). `payments.ts:57-60` then still reports `program: 'sponsor'`.
- The client really sends it: `leaders-app/src/screens/SignIn.jsx:38,95` pass `{ org, ref }` from `attribution.js` (derived from `document.referrer`), so the parameter is a documented, live input — but the server never validates provenance.

**Impact**
Anyone registering with any email (Gmail etc.) and `ref: "manzoma.sa"` (org domains are discoverable through the open `org.info`, L2, or from public partner listings) gets `org_via:'domain'`, is counted as a sponsored seat (`adminOrgFinance` over-seat/value reporting, `payments.ts:285-320`), receives the full program for free (`contract_cents` value pinned), lands in the org's cohort (`programs.ts:36-42` → cohort by `organization_id`; sees that cohort's hall, groups, workshop sessions, advisor), and appears in the org coordinator's dashboard and weekly report. Even after an admin notices and unlinks them, the pinned entitlement keeps the program free.

**Minimal fix**
1. Remove `orgByHost(hostOf(b.ref))` from `resolveOrg` at registration; keep `referrer_host` purely as analytics. Only `invite_code` (link/typed) and the *verified* email domain (`orgByEmail`, already applied after verification in `me()`:514-519) may set `organization_id`.
2. In `assignOrg` (and `adminDecide` reject), revoke live `entitlements` with `source='sponsor' and organization_id = <old org>` when a participant is moved away from an org.
3. Optionally keep `via:'domain'` for the `org.info` *display* only.

### H2. Eighty unauthenticated `auth.start` calls take every email-OTP login offline for 24 hours

**Evidence**
- `core.ts:326-329` `mailGuard`: if `challengeCount(dayAgo) >= CONFIG.mailDailyCap` (default 80, `core.ts:35`) → `429 mail_cap` for **everyone**.
- `participant.ts:180-199`: for an unknown email, supplying `full_name` (≥3 chars) makes `authStart` pass `mailGuard` and insert an `email_challenges` row (`:196-199`) — no account or prior relationship needed. Per-email limit is 5/h (`:174-176`) but attacker uses 80 distinct fake addresses; per-IP limit is 150/h (`core.ts:323`), above the cap.
- Turnstile is applied only `if (CONFIG.turnstileSecret)` (`core.ts:330`); `system.ts:52,58` treats it as an optional secret.
- The same guard fronts `coordinator.authStart` (`coordinator.ts:35`) and `experts.portalStart` (`experts.ts:440`), so coordinators and experts are locked out too. The gaps doc (§5) already notes the cap is close to real demand on workshop day.

**Impact** One actor, one IP, ~80 POSTs → platform-wide authentication outage for participants/coordinators/experts who use email codes, repeatable daily. With Turnstile configured, cost rises to 80 solved captchas (cheap via solver services) — still Medium.

**Minimal fix**
- Separate buckets: a per-IP/day cap (e.g. 10) and a per-purpose cap (registrations vs. logins), so new-registration spam cannot starve existing users' login codes.
- Count challenges only after successful `sendMail` (today the row is inserted before sending, `:196` vs `:201`).
- Make Turnstile mandatory for `purpose='register'` and for any IP over N/h; fail closed if the secret is missing.
- Alert (`LEADERS_ALERT_EMAIL`) when 70% of the cap is reached.

### H3. Contact form lets strangers send branded mail to arbitrary recipients and exhaust the shared Resend quota (new evidence on HANDOFF §5.1)

**Evidence**
- `home/assets/program/js/typeform.js:254-261` inserts directly into `public.contact_requests` with the anon key; `migrations/20261021120000_security_hardening.sql:57-64` limits to 3/h per email and 60/h globally — no per-IP limit, no captcha (grep of `typeform.js`/`home/index.html` for turnstile/captcha/honeypot: none).
- `send-otp/index.ts:91-104` `confirm` sends a "we received your request" mail to `r.email` — the address the submitter typed — once per contact row (`mail_log` claim, `:44-49`). `:66-88` `notify` sends to the owner per row. Neither checks Turnstile.
- Resend free plan is 100 mails/day (gaps doc §5); `mailGuard`'s daily cap (`core.ts:294`) does not count these at all.

**Impact** 60 contact rows/h → up to 120 mails/h from `no-reply@mail.sunkvalue.com` to attacker-chosen addresses (spam/phishing-adjacent reputation damage) and the daily Resend allowance is consumed in under an hour, which blocks OTP delivery for leaders-app, admin-api and user-api (same key). Combined with H2 this is a second, independent path to the same outage.

**Minimal fix** Turnstile on the form verified inside the `contact_requests_guard` trigger is not possible, so: (a) move inserts behind `send-otp` (or a new function) that validates Turnstile and a per-IP limit before inserting; (b) stop sending the `confirm` mail to unverified addresses (or make it a double-opt-in link with no branding/content); (c) count contact mails in the daily cap or send them with a separate key/domain.

## MEDIUM

### M1. Participant email enumeration oracle
`participant.ts:178-182`: `authStart` looks up `participants` and, for an unknown email without `full_name`, returns `{ needs_name: true }` *before* `mailGuard` (`:193`) and without inserting a challenge (so the 5/h per-email counter never increments). A registered email yields `sent:true` (or `429 rate` after 5). The comment at `:168` claims the opposite. Unlimited, captcha-free confirmation of who is enrolled in the leadership program.
**Fix** Run `mailGuard` first; always answer `{ success:true }`; ask for the name on the first screen for everyone (or after code verification using `purpose`), never branching on existence before the guard.

### M2. OTP attempt limit is bypassable by concurrency
`participant.ts:217-222`: reads `ch.attempts`, compares, then `update({ attempts: ch.attempts + 1 })`. Identical in `coordinator.ts:65-70` and `experts.ts:456-459`. N parallel requests all observe `attempts=0`; the limit of 5 only holds for sequential clients. 6-digit code, 15-minute TTL (`core.ts:38`). admin-api/user-api use insert-then-count (`admin-api:117-122,371`), which has the same window.
**Fix** Atomic guard: `update email_challenges set attempts = attempts + 1 where id = $1 and attempts < 5 returning attempts` (RPC) and fail if no row returned; add a per-IP verify limit; consume the challenge on the 5th failure.

### M3. Participant passkeys: no step-up to register, no removal, not revoked with sessions
- `passkeys.ts:37-51` `registerOptions(p)` accepts any valid participant session (14-day, localStorage). admin-api (`:484-487`) and user-api (`:298-303`) require fresh auth / passkey-method; leaders-api does not.
- Router `index.ts:118-120` exposes only `register-options`, `register-verify`, `dismiss` — there is no `passkey.list`/`passkey.remove` for participants. `sessionsRevoke` (`participant.ts:297-302`) touches `auth_sessions` only.
- No "new passkey added" notification (admin-api sends `securityMail`, `:533-535`).
**Impact** A token stolen via XSS/shared device is converted into a permanent credential the victim cannot see or revoke.
**Fix** Require `auth_sessions.method` ∈ {passkey, email_link/email_code/google} created < 10 min ago for registration; add list/remove actions; revoke all other sessions on removal; send `newDeviceMail`-style notice on registration.

### M4. HTML injection into transactional mail (including from an unauthenticated endpoint)
`_shared/mail.ts:20` provides `esc()`, but these interpolations skip it:
- `experts.ts:46-47` (open `expert.apply` → owner): `mailText(\`${fields.full_name}${fields.title ? ` · ${fields.title}` : ''}\`)` — attacker-controlled up to 120/160 chars, no auth.
- `experts.ts:558-559` (expert → owner), `:448` (expert's own name), `:221-222`, `:334`.
- `sponsor.ts:33-34` (participant → owner): `p.full_name`, `p.email`, `typed` (≤200 chars); `:72,80` (admin/org/participant text → participant).
- `advisor.ts:27-28` (participant name → advisor expert).
**Impact** Crafted `<a>`/`<table>` content renders inside the trusted Milestone template in the owner's/advisor's inbox — phishing the people with the most privilege.
**Fix** `esc()` every `${}` inside `mailText/mailNote`; add a vitest that greps `mailText(\`` templates for unescaped `${` (mail.test.js already exists as a home for it).

### M5. Demo account is not sandboxed
- `demo.ts:27-32` issues a normal 14-day sliding session (`issueSession(..., 'demo')`) and returns it in the URL fragment to be shown on a projector; `DemoTour.jsx:19-27` persists it in `localStorage`.
- `index.ts:86-149`: the demo participant can call every participant action; `payments.ts:51` returns `'demo'` for both items so `requireAccess` passes. No `is_demo` checks exist in `impact.ts`, `experts.ts`, `activities.ts`, `hall.ts` (grep confirms).
- Consequences: `rater.invite` (`impact.ts:244-276`) emails any address; `experts.choose` (`experts.ts:625-641`) creates `expert_requests` and emails real experts (`offerNext`, `:236-240`); `coaching.instant` (`activities.ts:227-247`) emails the coach; `sponsor.request` emails the owner; `hall.join/hand/pick` (`hall.ts:64-91`) enters the real default-cohort hall; `pay.checkout` (`payments.ts:78-111`) creates live Creem checkouts; `upload.url` consumes storage.
**Fix** In the router, when `p.is_demo`, allow only an explicit `DEMO_OK` set (me, profile, assessment, handbook/models/lab/katon reads, demo.fill-*) and reject the rest with 403; give `method='demo'` sessions a short absolute TTL (e.g. 8 h) and revoke them in `demo.reset`/`demo.open`.

### M6. leaders-api admin identity is a stale copy of role/active state
`admin.ts:22-29` validates `api_sessions.token_hash`/`expires_at` and returns `meta.role`/`meta.email`. admin-api's own `getAdminSession` (`admin-api/index.ts:124-138`) deliberately re-reads `admin_users` for `is_active`, `role_id` and `passkey_only` "so revocation applies immediately". Admin-api's `update-user`/`reset_access` do delete sessions (`:734,765`), so the gap is: deactivation/demotion done in SQL, `passkey_only` enforcement, or any future admin-api path that forgets `revokeSessions` — leaders-api keeps honouring the old role until the 4-hour expiry. Also HANDOFF §5.3 asked for exactly this contract.
**Fix** Select `subject` too and join `admin_users` (`is_active`, `role_id`, `passkey_only` vs `meta.method`) in `adminFromToken`.

### M7. `user-api register-send` is an open mail cannon
`user-api/index.ts:186-198`: validates format, 60 s cooldown per email, then `issueOtp` to any address. No per-IP cap, no captcha, no daily cap; `resume-send` is bounded by registered phones. Same Resend key/quota as H2/H3.
**Fix** Per-IP hourly/daily cap, Turnstile, global daily cap shared with `mailGuard`.

### M8. Booking webhook: replay and cross-participant credit
- `logic.js:1051-1053`: Cal.com verification is `sig === hmac(raw)` with no timestamp/nonce; `activities.ts:276-279` upserts on `external_id`, so a captured `BOOKING_CREATED` can be replayed after cancellation to resurrect a `booked` session (Calendly path has a 300 s window, `:1060`).
- `activities.ts:265-271`: target participant/requirement come from `metadata.ref` (`participant_id.requirement_id`, set by whoever fills the public booking page) — the attendee `email` parsed at `logic.js:1022` is never compared with `participants.email`. Anyone who knows a participant UUID (coordinators, experts, cohort peers via hall/groups payloads) can book on the public link and have the session credited to that participant.
**Fix** Compare `e.email` with the participant's email (or sign `ref` with HMAC like QR tokens); reject Cal.com events whose `createdAt`/`uid` were already processed (`payment_events`-style table); non-constant-time compare → use the `same()` helper from `payments.ts:138`.

### M9. Long-lived bearer tokens in `localStorage`
`leaders-app/src/api.js:8-14,66-71,94-99` keep participant, coordinator and expert tokens in `localStorage`; `participant.ts:61-65` renews expiry on every call with no absolute maximum, so an active token never expires. Coordinator sessions carry organisation-wide PII. Admin uses `sessionStorage` + 4 h server TTL (good).
**Fix** Absolute lifetime (e.g. 30 days from issue) in `participantFromToken`/`fromToken`/`expertFromToken`; `sessionStorage` (or shorter TTL) for coordinator/expert portals; keep "remember me" explicit.

## LOW

- **L1 Unbounded challenge inserts.** `passkeys.ts:82-86` `authOptions()` is open with no `challengeFlood` (admin-api `:248-253`, user-api `:163-168` have one). No purge of `leaders.webauthn_challenges`, `email_challenges`, `coordinator_challenges`, `expert_challenges` (grep: no delete/cron). Fix: per-minute global cap + cron purge of expired rows.
- **L2 `org.info` guessing.** `participant.ts:160-164` is open and unlimited; `orgByCode` (`:74-79`) accepts 4–40 char codes (admin may set short codes; default is 8 hex chars, `admin.ts:757`). `sponsorByCode` has 10/h (`:118-124`) but `org.info` bypasses it; `ref` also reveals org name/colour per domain. Fix: rate-limit by IP; drop `ref` resolution (H1).
- **L3 Tokens in URL / immortal links.** `Rater.jsx:12`, `Sponsor.jsx:12`, `Outcome.jsx:13`, `ExpertOffer.jsx:15` read `?t=` and never `replaceState` (Verify/Org/App do). Server side: `capstone.ts:343-349` and `tracking.ts:122-131` only enforce expiry while `pending`, and never null the hash after a decision; `experts.ts:329` leaves `offer_token_hash` on accept, so `offerGet` (`:309-322`) keeps revealing the participant's full name indefinitely. Fix: strip `t` after read; clear hash / enforce expiry in terminal states.
- **L4 `expert.apply` email squatting.** `experts.ts:24-50` creates an `experts` row for any email with no verification (5/h per IP, `mailGuard` not used → bypasses daily cap/Turnstile, sends 2 mails). Consequences: `adminSave` refuses to invite that email (`:98-99`), `rolesOf` now reports an expert role so the real person's registration shows `choose_role` (`participant.ts:229-232`) and `wrongDoor` mails fire. Fix: verify the email (code) before inserting; reuse `mailGuard`.
- **L5 Viewer-role surface & unscoped signed URLs.** `admin.ts:290-295` signs any `b.path` in `leaders-private` (no `participant_id/` prefix check as in `cvAttach`); `activities.ts:348-358` `admin.workshop-qr` returns a live check-in token to `viewer` admins (no verb → not covered by `authz.test.js:14-16`); viewers also read `hourly_rate`/`admin_note`/`applied_ip` (`experts.ts:63-79`) and `missing_secrets` (`system.ts:47-58`). Fix: path-prefix check; gate QR behind `requireWrite`; extend the authz test with an explicit allow-list of viewer-safe reads.
- **L6 IP trust.** `core.ts:72-73` / `admin-api:171-174` prefer `cf-connecting-ip` then first `x-forwarded-for` hop. Correct behind Cloudflare; if the function URL is ever reachable without it, every per-IP limit (mailGuard, cert verify 40/10 min, `expert.apply` 5/h, sponsor-code 10/h) and audit IP becomes attacker-chosen. Fix: document/verify the header origin; never fall back to XFF[0].
- **L7 CSP.** `home/_headers:11` `script-src 'self' 'unsafe-inline'` on the site that embeds the anon key and contact form; `frame-ancestors 'self'` (home, matrix) vs `'none'` (admin, leaders); `media-src https:` broad in leaders; no `report-to`. Admin/leaders policies are otherwise strict.
- **L8 PII in repo.** `send-otp/index.ts:16` hardcodes `p.o.m2012@hotmail.com`; `migrations/20261022110000:4,25` hardcodes the owner Gmail. Move to env/vault. (No service keys or private secrets found in the tree; only the anon JWT.)
- **L9 Cap under-counting.** `core.ts:294` `CHALLENGE_TABLES` omits `expert_challenges`; `experts.ts:446` inserts there and `apply` mails are uncounted — the health report (`system.ts:42-46`) under-reports usage.
- **L10 Signature image exposed.** `certificates.ts:100-101` puts `signatory.image` (base64 PNG) in the snapshot and `:195` returns the whole snapshot from the public `cert.verify`. Enables realistic forged print-outs. Fix: strip `image` from the public verify payload.
- **L11 TOTP replay.** `admin-api/index.ts:97-102` accepts the same code within ±1 window; store last accepted counter per user.
- **L12 MFA asymmetry.** `admin-api/index.ts:424-426` gates writes by role only; leaders-api additionally requires passkey/TOTP (`admin.ts:34-37`). `add-user`/`update-user` by a super_admin logged in with an email code are higher-impact than most leaders-api writes.
- **L13 PostgREST filter interpolation.** `admin.ts:220-223` strips `[%,()]` then builds `.or('full_name.ilike.%s%,...')`; `activities.ts:31` strips `[,()]` from webhook `organizer.email` into `.or('email.eq.…,full_name.eq.…')`. Not exploitable with the current grammar but blacklist-based; prefer `.ilike()` builders / `textSearch` or a strict allow-list regex.
- **L14 Audit/log hygiene.** `core.ts:133-136` stores full `before/after` rows (`coordinator.update` → phone/email; `expert.update` → hourly_rate/admin_note); `participant.ts:908` and `certificates.ts:186` store IP + UA per view/check with no retention. `must()` (`core.ts:102-107`) logs raw DB errors.

## Test coverage gaps (what existing tests do not catch)
