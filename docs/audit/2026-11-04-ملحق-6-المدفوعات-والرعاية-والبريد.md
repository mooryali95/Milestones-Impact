## 1. Entitlement model

### What exists (verified)
- **One authoritative function**: `access(p)` in `supabase/functions/leaders-api/payments.ts:48-69`. Sources, in order: demo (`p.is_demo` → `'demo'`, line 51), active sponsor org (`sponsorOf`, 31-35; pinned into `entitlements` with `source='sponsor'`, 37-46), `entitlements` rows (`paid | admin | grandfathered | sponsor`, migration `20261104130000:4`), and the global kill-switch `payment_settings.enabled=false` → `'free'` (line 67).
- **One table**: `leaders.entitlements` with a partial unique index "one live row per (participant,item)" (`20261104120000_leaders_payments.sql:45-57`). Items: `assessment`, `program` (`payments.ts:13-15`).
- **One gate**: the router. `index.ts:82-89` defines `PAY_FREE` + `payGate()`; `index.ts:309-312` calls `requireAccess` (`payments.ts:72-75`, 402 + code `pay:<item>`) for every participant action not in `PAY_FREE`. `assessment.*` needs `assessment` unless `kind==='post'` (then `program`), consistent with `participant.ts:610`. Journey, handbook, models, lab, hall, katon, capstone, tracking, `certificate` (mine) all fall under `program`.
- Paywall UI (`leaders-app/src/screens/Paywall.jsx`) never grants; it polls `me` for up to 45 s after return (`47-59`). Good.
- Grandfathering was a one-off in the migration (`20261104120000:70-75`).

### Findings

**E1 — Pinning is lazy, not "at link time" (Medium).**
`pinSponsor` is only called from `access()` when the participant next hits any gated action or `me` (`payments.ts:55-56`). None of the link paths pin: `admin.assignOrg` (`admin.ts:108-125`), `sponsor.adminDecide` (`sponsor.ts:68`), `sponsorCode` (`participant.ts:154`), registration (`participant.ts:189,243,272`), domain re-link (`participant.ts:517`). Impact: `adminOrgFinance` shows `value_cents: null` and `joined = created_at` for everyone linked by admin who has not logged in since (`payments.ts:294-303`); if `contract_cents` changes between link and first login, the "pinned" value is the later one. The PR #173 claim and `OrgFinance.jsx:4` comment are not met. Fix: call `pinSponsor` from the link sites (export it), keep the `access()` call as a fallback.

**E2 — Refund/dispute revokes the entitlement but not the outcome (Medium).**
`revokeFor` (`payments.ts:128-130`) only flips `entitlements.revoked_at`. `issueOnCompletion` (`certificates.ts:163-171`) and `setStatus` (`admin.ts:325-333`) do not consult `access()`; a chargeback after completion leaves status `completed` and a publicly verifiable certificate. The admin "review" list (`payments.ts:211-212`) only covers paid-then-sponsored, not refunded-after-progress. Fix: on `refund.*`/`dispute.created`, add the participant to a review list in `adminOverview` and show a banner in the participant profile; optionally auto-revoke a certificate issued after `paid_at`.

**E3 — Turning payments on later locks out people who joined while it was off (Medium).**
With `enabled=false`, `access()` returns `'free'` without writing rows (`payments.ts:67`); `adminSettings` (`234-251`) does not grandfather on enable. The confirm text in `Payments.jsx:31` says "المشاركون الحاليون معفون", which was only true for the migration cohort. Fix: on `enabled: false→true`, insert `grandfathered` rows for participants with `created_at < now()` (same statement as the migration), or gate by `created_at >= enabled_at`.

**E4 — Moving/unlinking a participant keeps the old org's sponsor rows (Medium).**
`assignOrg` with `participant_ids` updates `organization_id` freely (`admin.ts:118-121`; UI "نقل إلى جهة" `Orgs.jsx:199-205`). `access()` re-pins only *missing* items (`payments.ts:56`), so rows stay `source='sponsor', organization_id=<old org>`: the participant keeps free access after an unlink-by-mistake (e.g. wrong domain), org A's statement no longer lists them but their value is orphaned, org B shows `null`. Fix: in `assignOrg`, revoke live `sponsor` rows of the previous org (revoked_by=admin, note) and pin the new org; surface this in the confirm dialog.

**E5 — Paid-both-items then linked is invisible (Low).**
Both `pinSponsor` inserts hit the unique index (`payments.ts:43-44`), so `sponsoredIds` (`211`) never includes them and they are absent from "للمراجعة"; org finance lists them at `null` value. Fix: compute `review` from `participants.organization_id IS NOT NULL ∩ paid`, not from sponsor rows.

**E6 — Test-mode payments grant real entitlements (Low).**
`settle` ignores `pay.mode` (`payments.ts:114-126`); one webhook secret serves both modes (`19,141`). If the test key is left in secrets while `enabled=true`, test checkouts unlock the program. Fix: in `settle`, require `pay.mode === modeOf(apiKey())` and refuse `test` when `settings.enabled`.

**E7 — `contract_starts/ends` are informational only (Low).**
`sponsorOf` checks `status==='active'` only (`payments.ts:34`); an expired contract still exempts new registrants. Fix: add date window to `sponsorOf` (and show "contract expired" in OrgFinance).

**E8 — No bypass found in the participant router (Info).**
Every participant action passes `payGate`. `me` intentionally returns level/track before payment (`Paywall.jsx:90-95`). Admin, advisor, expert and coordinator paths are not gated by design; `cert.verify` is public by design. `switchTo` issues participant sessions that are then gated normally (`switch.ts:19-22`).

**E9 — No automated coverage for the money path (Low).**
No test file references `payments.ts`, `settle`, `webhook` or `access` (only `leaders-app/src/activities.test.js` touches booking webhooks). CI type-checks only `leaders-api/index.ts` (`.github/workflows/ci.yml:53`), so `creem-webhook/index.ts` is never checked. Fix: unit tests for `webhook()` (dup, out-of-order, refund, bad signature, amount mismatch) with a stubbed `db`; add `deno check supabase/functions/creem-webhook/index.ts`.

## 2. Payment lifecycle (Creem)

### What exists (verified)
- Checkout: server-side `POST {apiBase}/v1/checkouts` with `product_id`, `request_id = payments.id`, `success_url=/?paid=<item>`, `customer.email`, `metadata` (`payments.ts:93-101`); row inserted first with expected `amount_cents/currency/mode` (`89-92`); 5 checkouts/hour/participant (`86-88`); failures mark `failed` (`103-107`).
- Webhook: separate function with `--no-verify-jwt` (`creem-webhook/index.ts:3,9-19`); HMAC-SHA256 hex over the raw body in header `creem-signature`, constant-time compare (`payments.ts:132-144`); idempotency by `payment_events.event_id` unique (`148-149`, migration `59-68`); handles `checkout.completed`, `refund.*`, `dispute.created` (`151-162`); 5xx → Creem retries.
- Reconcile: admin `GET /v1/checkouts?checkout_id=` → settle on `completed`, mark `expired` (`269-282`).
- Admin: KPIs on live+paid only, refunds separate (`195-227`), CSV export, test/live filter (`Payments.jsx:88-96,129-140`).

### Findings

**P1 — Failed processing is permanently stuck (High).**
`payment_events.insert` runs before the `try` (`payments.ts:148`); if `findPayment` returns null or `settle` throws (`153,123`), the row stays with `error` set and `processed_at` null. Creem retries with the same `id` → `23505` → `{duplicate:true}` 200 (`149`) → never reprocessed. The admin sees only "N إشعار تعذّرت معالجته" (`Payments.jsx:48`) with no retry button. Fix (minimal): on `23505`, load the existing row and, if `processed_at IS NULL`, process it again instead of returning; or delete the row in the `catch`.

**P2 — Out-of-order / late `checkout.completed` re-grants after refund (Medium).**
`settle` guards only `status==='paid'` (`115`); a refunded row becomes `paid` again and a new entitlement is inserted (`117-123`). Fix: `if (pay.status !== 'pending') return;` and log.

**P3 — No amount/currency/product validation (Medium).**
`settle` writes whatever the event carries (`118-119`) and never compares with `pay.amount_cents/currency/product_id` captured at checkout (`90-91`). The admin UI even says prices are display-only and must be kept identical by hand (`Payments.jsx:63`). A product price changed in Creem (or a discount code) is silently accepted; KPI revenue sums raw cents across possibly different currencies (`197-201`). Fix: compare `obj.order.amount`, `obj.order.currency`, `obj.product?.id`; on mismatch settle with `note:'mismatch'`, do not grant, and list under review.

**P4 — Any `refund.*` is treated as full (Medium).**
Partial refunds (Creem supports them) revoke the whole entitlement (`155-161`). Fix: compare `obj.amount`/`refund_amount` with order amount; partial → note + review only.

**P5 — Events without `id` / malformed JSON (Low).**
`event_id: ev.id || null` is never deduped and never gets `processed_at` (`148,163`); `JSON.parse` before the try (`145`) → 500 → infinite retries on a malformed body. Fix: parse inside try; reject with 400 when `!ev.id`.

**P6 — No terminal state for abandoned checkouts (Low).**
`checkout.expired` / failed payment events are ignored; `pending` rows live forever unless an admin clicks "تحقق من Creem" (`Payments.jsx:158`) and they count in the "دفعات معلّقة" KPI (`payments.ts:225`). Fix: handle `checkout.expired`, or expire `pending` older than 24 h in `cron.expert-offers`.

**P7 — Webhook function deploys are manual and can drift (Medium).**
`deploy-leaders-api.yml` triggers only on `leaders-api/**` and `_shared/**` and deploys only `leaders-api` (`11-12,44`). `creem-webhook/index.ts:7` imports `../leaders-api/payments.ts`; no `supabase/config.toml` exists, so `verify_jwt` must be disabled by hand each deploy (`creem-webhook/index.ts:3`). Fix: add `supabase functions deploy creem-webhook --no-verify-jwt` (and `leaders-hooks`) to the workflow, or a `config.toml` with `[functions.creem-webhook] verify_jwt = false`.

**P8 — Currency model: one fixed USD, cents of that currency (Medium).**
`payment_settings.currency` defaults to `USD` (`20261104120000:11`) and is **not** editable (`adminSettings` patch omits it, `payments.ts:238-244`). Hence `contract_cents` = USD cents (`payments.ts:39`), and `1,000,000` = $10,000 (doc item 6). UI hard-codes `$`/USD: `Payments.jsx:52-56`, `OrgForm.jsx:317` ("السعر التعاقدي للمشارك (USD)"), `OrgFinance.jsx:10,21` (CSV header "القيمة (USD)"), `SponsorNote.jsx:34`, `Paywall.jsx:10`. Yet the same org-facing surfaces show capstone costs in ريال (`Sponsor.jsx:189`, `OrgPortal.jsx:113`). The webhook may overwrite `payments.currency` with Creem's (`119`), after which `adminOverview` adds cents of mixed currencies. Build-on for item 6: beyond the typo, there is no place to say "this contract is in SAR". Fix: `organizations.currency` (default SAR) + `contract_cents` meaning cents of that currency; `entitlements.currency` captured at pin time; `Intl.NumberFormat('ar-SA',{currency})` everywhere; make `payment_settings.currency` editable only while no live `paid` rows exist.

**P9 — VAT / ZATCA / receipts (Medium; partly unverifiable).**
No tax logic exists anywhere; `Paywall.jsx:98` shows a bare price ("دفعة واحدة · بطاقة أو Apple Pay") with no "شامل/غير شامل ضريبة القيمة المضافة" statement (KSA E-Commerce Law requires total price disclosure). Receipts are delegated to Creem (`Paywall.jsx:101` "يصلك الإيصال") — nothing in the repo sends one. Organization contracts are not transacted or invoiced anywhere: `OrgFinance` produces an informational CSV (`OrgFinance.jsx:20-23`), which is not a tax invoice; if the Saudi entity invoices orgs in SAR it must issue ZATCA-compliant e-invoices (Phase 2 integration: XML/QR, VAT number, 15% line). The public `refund.html` describes a 14-day subscription refund for the Matrix product (`143-196`) and is not linked from the Paywall; the webhook's refund handling (full revoke) is not described anywhere participants can read.
Cannot verify from repo — owner checks: (a) Creem dashboard → Settings → Taxes: confirm Creem acts as Merchant of Record and charges KSA VAT (15%) on B2C sales, and that customer receipts/invoices are enabled; (b) whether Milestone Impact's legal entity is VAT-registered in KSA and which ZATCA phase applies; (c) decide whether org contracts are invoiced outside the platform (then the CSV must say "statement, not an invoice").

**P10 — Signature scheme (Low; unverifiable).**
Implementation matches Creem's documented scheme (HMAC-SHA256 hex of raw body, header `creem-signature`). Owner checks: Creem → Developers → Webhooks: URL exactly `https://eormhcupwgwpllhrfxxg.supabase.co/functions/v1/creem-webhook` (shown in `Payments.jsx:52`), events `checkout.completed`, `refund.created`, `dispute.created` enabled, secret equal to `CREEM_WEBHOOK_SECRET`/`CAREEM_WEBHOOK_SECRET`; test and live endpoints configured separately (each mode has its own secret — the code holds only one, see E6).

**P11 — Settings and grants (Low).**
`adminSettings` refuses to enable without key, secret and both product ids (`payments.ts:245-247`) — good. `adminGrant` revoke hits `paid` rows with no refund (`258-261`) behind a confirm (`Payments.jsx:118`) — acceptable. `PersonAccess` loads the full 7,000-row overview per profile view (`Payments.jsx:252-256`) — performance only.

## 3. Sponsorship and organizations

### What exists (verified)
- Org row: `status` free text default `'active'`, `seats`, `invite_code`, `domains text[]` (`supabase/schema/baseline.sql:714-739`); contract columns added in `20261104150000`.
- Attribution precedence: typed sponsor code → link code/referrer host (`resolveOrg`) → verified email domain (`participant.ts:142-144`); on later logins `me()` auto-links by domain once (`512-521`). Public mail domains excluded (`131-133`).
- Sponsor requests: `pending|approved|rejected|cancelled`, one pending per participant (`20261104140000:7,14`); admin matching via `sponsor-match.js` (tests in `leaders-app/src/sponsor-match.test.js`).
- Coordinators/viewers: one table `org_coordinators` (`20261023120000`, multi-viewer since `20261030180000`), statuses `invited|active|suspended`, templates `executive|program|hr|custom`, `expires_at` (`logic.js:717-740`).
- Org finance: `adminOrgFinance` (`payments.ts:285-320`) + `OrgFinance.jsx`.

### Findings

**S1 — Parent-domain matching with no public-suffix guard (High).**
`orgByHost` builds candidates from every suffix except the TLD (`participant.ts:94-96`): for `x@mail.moh.gov.sa` → `mail.moh.gov.sa`, `moh.gov.sa`, `gov.sa`. The admin form accepts any `label.tld` (`OrgForm.jsx:16`), so an org saved with `gov.sa`, `com.sa` or `edu.sa` (plausible when an admin "wants all government staff") auto-links and exempts every such registrant and exposes them to that org's viewers; the UI hint even encourages domain entry (`OrgForm.jsx:342`). `PUBLIC_MAIL` is a 19-entry list (no `ymail.com`, `mail.ru`, `qq.com`, `pm.me`, `fastmail.com`, `hey.com`, country-code Outlook/Yahoo variants). Fix: reject domains that are public suffixes (ship a small PSL subset incl. `gov.sa`, `com.sa`, `edu.sa`, `org.sa`, `net.sa`, `sch.sa`, `med.sa`) in `admin.save` for `organizations` and in `orgByHost`; require ≥ 2 labels under a public suffix; extend the free-mail list.

**S2 — Silent auto-link = silent disclosure (Medium, PDPL).**
`me()` links by domain without telling the participant (`participant.ts:512-521`, only an audit row). `notifyNewAccess` (`coordinator.ts:261-272`) fires only when an org's *permission union widens*, so a participant joining an org that already has an `hr` viewer (contact on) gets no notice although the mail template promises transparency "قبل الاطلاع" (`core.ts:248-254`). Fix: send `orgAccessMail` on any link (`domain|link|admin`) when `orgVisibility(viewers).viewers > 0`, and show a persistent "جهتك ترى…" line in the profile with a "هذا خطأ؟" action (creates a sponsor-unlink request).

**S3 — Two orgs with the same domain → nondeterministic owner (Medium).**
`orgByHost` takes the first hit per candidate without `order()` (`participant.ts:96-99`); no uniqueness on `unnest(domains)`; `sponsor-match` would score both. Fix: validate in `admin.save` that no other org holds the domain; add a DB-level check via trigger or a normalized `org_domains(domain unique)` table.

**S4 — Email change / subdomains / look-alikes (Low).**
Participants cannot change email (`PROFILE_FIELDS` `participant.ts:537-539` excludes it; admin `ENTITIES` has no participants entry `admin.ts:415-440`), so "changed email" cannot happen in-app; the link persists regardless. Subdomain matching (`endsWith('.'+d)`) is intended; look-alikes (`manozma.sa` vs `manzoma.sa`, doc item 4) do not match (safe direction). `isEmail` (`logic.js:406`) accepts non-ASCII labels; `orgByHost` lowercases but does not punycode — a homograph domain would simply not match (safe).

**S5 — Three different definitions of an "active" org (Medium).**
`live()` = `status !== 'inactive'` (`participant.ts:72`); `viewerActive` = `organizations.status !== 'inactive'` (`logic.js:733-734`); `sponsorOf` = `status === 'active'` (`payments.ts:34`); `adminDecide` requires `'active'` (`sponsor.ts:66`). `status` has no CHECK (`baseline.sql:721`); the form only toggles `active|inactive` (`OrgForm.jsx:264-266`) but any other value (import, typo, future "paused") would attribute and expose participants to coordinators **without** exempting them → paywall for sponsored people. Fix: `CHECK (status IN ('active','inactive'))` + one `orgActive()` helper used by all four sites.

**S6 — Seats are a label, not a control (Low).**
`over_seats` is computed by join order (`payments.ts:300-305`) and only flagged; nothing alerts admin or coordinator when exceeded; the coordinator sees "N من S مقعد" (`OrgPortal.jsx:217`) with no over-seat indicator; weekly health mail does not mention it (`system.ts:162-167`). Fix: include `over` in `coord.dashboard` and in `weeklyHealth.issues`.

**S7 — Sponsor-request workflow edges (Low).**
States are correct and one-pending is enforced. Gaps: (a) a participant who later enters a code (`sponsorCode` `participant.ts:150-157`) or is linked by admin leaves the request `pending` forever (admin queue clutter; `access()` hides it only because `sponsor` exists, `payments.ts:65-66`); (b) `contact_email` is stored (`sponsor.ts:27-29`) but never used; (c) the new-request alert goes to `LEADERS_ALERT_EMAIL` fire-and-forget (`32-35`) — if that secret is unset nobody is told except via the admin tab. Fix: cancel pending requests inside every link path; use `contact_email` to pre-fill a coordinator invite.

**S8 — Coordinator invite state machine (Low).**
`invited` → `active` on first login (`coordinator.ts:87`, also via switch `switch.ts:34`); `suspended`/resume (`295-306`) revokes sessions; email change re-invites and revokes (`242-247`); delete is hard delete with audit (`317-324`); viewer expiry is `expires_at` (`logic.js:733`). The invite mail carries no token and never expires (`core.ts:230-236`), so "resend" is always valid. Gaps: `adminInvite` sends to an expired viewer (checks only `suspended`, `280-289`) who then gets a wrong-door/no-op at login; coordinator email uniqueness is app-enforced only (`229-231`; DB has a non-unique index `20261023120000:27`) and `coordinatorByEmail().maybeSingle()` (`25`) would 500 on a duplicate. Fix: `create unique index on org_coordinators (email)`; refuse invite when `expires_at < now()`.

**S9 — Viewers vs coordinators: permissions are sound (Info).**
Same table; `coordParticipant` (`logic.js:746-757`) strips by permission; `executive` sees aggregates only; contact/scores off by default (`717-721`); impact suppressed below `MIN_COHORT=5` (`coordinator.ts:160`); capstone doc only after approval and org-checked (`capstone.ts:408-414`); org derived from session, never from body (`index.ts:314-317`). Gap: the transparency mail's `SENSITIVE` list (`coordinator.ts:262`) omits "approved initiative documents" and "impact comparison with names", both visible to viewers (`166-178`, `OrgPortal.jsx:199`).

**S10 — Org statement (OrgFinance) arithmetic (Medium).**
`per_participant` divides total value by all rows including `null`-valued ones (E1) (`payments.ts:313-314`) → understated; `certified` counts any `certificates` row including revoked/replaced (`292,303` select `certificates(id)` with no status filter) → `per_certified` wrong after a revocation; `list_cents` uses today's settings (`311`) while values are historical; revoked sponsor rows are dropped (`295`) but the participant still appears with `null`. Fix: `certificates!inner(status)` filtered to `valid`; average over valued rows; show "غير مثبّت بعد" explicitly; add currency (P8).

**S11 — Sponsor KPI labels (Low).**
`adminOverview.sponsors` groups by `e.note` (org name at pin time, `payments.ts:207`) → renamed orgs appear twice; UI says "بأسعار اليوم" (`Payments.jsx:197`) but code uses pinned values when present (`209`). Fix: group by `organization_id`, join name, fix label.

## 4. The three doors

### What exists (verified)
- Routes: `/` participant, `/x` expert, `/org` coordinator (`doors.ts:139-143`, `leaders-app/src/Doors.jsx:6-10`); `rolesOf(email)` reads the three tables (`doors.ts:146-157`); every sign-in screen shows the other doors (`Doors.jsx:20-27`).
- Expert and org doors: `mailGuard` first, then lookup, then uniform `SENT`; non-members get `wrongDoor` mail if they hold another role (`experts.ts:437-442`, `coordinator.ts:31-37`, `doors.ts:159-169`, 1/hour/door/email via `audit_log`).
- Participant door: new registrations by an email that is an expert/coordinator must `choose_role`/`confirm_new` after proving ownership (`participant.ts:218-222,261-263`); Google on the expert door reveals doors only for a verified identity (`experts.ts:474-478`); `switchTo` never creates accounts (`switch.ts:14-38`).

### Findings

**D1 — Participant door is an email-enumeration oracle (High).**
`authStart` looks up `participants` and returns `{needs_name:true}` for unknown emails **before** `mailGuard` (`participant.ts:179-184` vs `mailGuard` at `194`); registered emails proceed to send and return `{sent:true}`. The per-email limit (`175-177`) counts `email_challenges` rows, which that path never inserts, so probing is unlimited and captcha-free. This contradicts the code comment (`166-167`) and allows anyone to confirm that a named person is enrolled in the leadership program (PDPL disclosure; phishing targeting). Minimal fix: run `mailGuard(b, ctx)` before the lookup (IP limits + Turnstile apply), and record a lightweight probe row so the per-IP counters grow; better: collect name+email in one step for unknown emails and answer uniformly (`sent:true`) — the SPA can still ask for the name after verification.

**D2 — Wrong-door mail: unsolicited-mail vector, cap bypass, timing leak (Medium).**
Anyone can make the platform mail a registered participant from the expert and org doors (1/hour/door → up to 48/day per victim) by typing their address (`doors.ts:162-168`). These mails are not counted in the daily cap (`core.ts:287-301` counts challenge rows only) nor logged. `await wrongDoor()` awaits `sendMail` (`168`), so response latency reveals whether the email has a role elsewhere (hundreds of ms vs none) — a weak but real enumeration side channel on the uniform-response doors. Fix: respond first and send asynchronously (`EdgeRuntime.waitUntil` or fire-and-forget), cap wrong-door mails per email per day (e.g. 2) and per IP, and count them in the cap/log.

**D3 — Dead-ends by design (Low).**
Rejected/suspended expert, expired viewer, `inactive` org, or a participant with no other role get "sent" and no mail (`doors.ts:160-161`); the UI only says "إن كان بريدك مسجلًا…" (`OrgPortal.jsx:70`). Acceptable for anti-enumeration; add a support line (`mi@sunkvalue.com`) under the code step.

**D4 — Suspended participant still receives OTPs (Low).**
`authStart` does not filter `status='suspended'` (`participant.ts:179`); the code is sent, then `participantFromToken` rejects (`60`). Wastes cap and confuses the user. Fix: check status before sending (uniform response).

## 5. Email (Resend)

### What exists (verified)
- Provider: Resend REST (`_shared/mail.ts:113-129`); from `Milestone Impact <no-reply@mail.sunkvalue.com>`, reply-to `mi@sunkvalue.com` (`95-96`); HTML + generated plain text (`101-109`); fallback sender `milestoneimpact@basserh.com` on 403/422 (`97-98,121-125`).
- Guard: `mailGuard` (`core.ts:287-301`): 150/h and 300/day per IP, global `LEADERS_MAIL_DAILY_CAP` (default 80) over `email_challenges + coordinator_challenges` in a rolling 24 h, then Turnstile if configured.
- Health: `system.ts:41-46,59` reports today's count vs cap; weekly mail warns at 80 % (`165`).
- Scheduling: pg_cron `leaders-weekly-reminders` Sun 06:00 UTC and `leaders-expert-offers` hourly at :17, both `net.http_post` to `leaders-api` with the Vault secret (`20261023090000:16-30`, `20261031110000:31-47`); `cron.reminders` chains participant reminders → tracking reminders → coordinator weekly → owner health (`index.ts:51-54`); `cron.expert-offers` chains offer sweep → session reminders (`70`). `leaders-hooks` is **not** a scheduler: it receives Cal.com/Calendly booking webhooks, HMAC-verified (`leaders-hooks/index.ts`, `activities.ts:251-281`).
- Gallery: 15 templates built by the same functions that send (`core.ts:252-268`, `MailGallery.jsx`).

### Findings

**M1 — Cap semantics (High, operational; builds on doc item 5).**
The 80/day cap is independent of Resend's real quota and counts the wrong thing: (a) only `email_challenges` + `coordinator_challenges` — `expert_challenges` is excluded (`core.ts:255`, `experts.ts:446`), so expert OTPs neither count nor appear in health; (b) rows are inserted before sending (`participant.ts:193-197` then `199`), so a Resend failure still consumes cap; (c) wrong-door, new-device, rater, sponsor, expert-offer mails and every bulk run are uncounted: `notifyNewAccess` can send up to 500 in one admin click (`coordinator.ts:268-271`), participant reminders 200/run (`admin.ts:922`), coordinator weekly 500 (`coordinator.ts:337`), tracking 500 (`tracking.ts:193`), session reminders 200 (`activities.ts:450`). On the free Resend plan (100/day, 2 req/s) a single `notifyNewAccess` can exhaust the day before the workshop's OTPs. What happens when hit mid-flow: `mailGuard` throws `429 mail_cap` with a visible message (`core.ts:296-298`) → sign-in is **not** silent but is blocked for everyone without a passkey/Google for up to 24 h; when Resend itself refuses, `deliver` returns false → `sendMail` throws `502 mail_failed` (`core.ts:124-128`) → shown by `SignIn.jsx` as `r.message`. Fix: one `leaders.mail_log` written by `sendMail` with `kind`; cap = reserved OTP budget (e.g. 70 % of plan) + separate bulk budget; move bulk sends to a queue drained by the hourly cron; include experts.

**M2 — No delivery log for the program (Medium).**
`public.mail_log` exists only for the contact form with `kind in ('notify','confirm')` (`20261022030000:7-13`, `send-otp/index.ts:44-49`). `leaders-api` keeps no record of what was sent to whom, and `deliver()` discards Resend's message id (`mail.ts:121-127`). Support cannot answer "did the code go out?", and there is no basis for bounce handling or per-recipient caps. Fix: `leaders.mail_log(to_hash, kind, subject, resend_id, status, error, created_at)` written in `sendMail`.

**M3 — Reminders are marked sent before sending; failures are swallowed (Medium).**
`reminded_at` is set then `sendMail(...).catch(console.error)` (`admin.ts:928-929`); same pattern in `coordinator.ts:345-346`, `activities.ts:453-459`, `tracking.ts:204-208`. A Resend outage or quota hit silently drops a week's reminders (or a session's 24-h reminder) with no retry. Fix: set the marker after a successful send, or write a `mail_log` failure row and retry next run.

**M4 — Nothing detects a dead scheduler (Medium).**
Both cron jobs live in migrations that are run by hand ("الترحيلات تُشغَّل يدويًا", `system.ts:4-6`) and require `vault.create_secret('…','leaders_cron_secret')`, `pg_cron` and `pg_net` (`20261023090000:8-12`). If any is missing, `net.http_post` sends `secret: null` → `403 forbidden` (`admin.ts:917`, `experts.ts:349`) and nothing is logged on the app side. `health()` checks only that `LEADERS_CRON_SECRET` is set and that the `reminded_at` column exists (`system.ts:14,50`), not `cron.job` / `cron.job_run_details`. The weekly health mail that would warn the owner is sent **by the same cron** (`index.ts:51-54`). Consequences if nothing fires: no weekly reminders, no coordinator summaries, no owner report, expert offers never expire to the next expert, no "جلستك غدًا" reminders. Fix: a `cron_runs(action, ran_at, result)` row written at the top of each cron action; `health()` reports "last run N hours ago" and `readiness` turns red after 25 h / 8 days; add a GitHub Actions `schedule` fallback that POSTs the same action with `LEADERS_CRON_SECRET` from repo secrets (the repo already has a scheduled workflow, `backup.yml:13-14`).

**M5 — No unsubscribe for recurring mails (Medium).**
Weekly participant reminder (`core.ts:155-160`), coordinator weekly (`238-245`, footer says only the admin can stop it), tracking reminders (`tracking.ts:205-208`) carry no `List-Unsubscribe` header or opt-out link; the only control is `org_coordinators.weekly_report` set by admin. Resend supports custom headers. Fix: `participants.reminders_opt_out_at`, a signed one-click opt-out action (`open` action with token), and `List-Unsubscribe`/`List-Unsubscribe-Post` headers on those kinds.

**M6 — No bounce/complaint handling (Low).**
No Resend webhook endpoint and no suppression list (grep: no `bounce|complaint` handlers). Repeated OTPs to a dead address keep burning cap and reputation. Fix: Resend webhook (`email.bounced`, `email.complained`) → `mail_suppressions`; `sendMail` refuses suppressed addresses.

**M7 — Silent sender fallback (Low).**
On 403/422 the mail is re-sent from `basserh.com` (`mail.ts:121-125`): different From domain, DMARC alignment of the fallback unknown, recipients see an unexpected sender; the comment says it exists for a key restricted to the old domain. Fix: remove once the new domain is verified; alert instead.

**M8 — Template drift outside the gallery (Low).**
`MAIL_GALLERY` has 15 entries (`core.ts:252-268`) but ~20 mails are assembled ad hoc with `mailShell/shell` elsewhere: `experts.ts` (10 call sites), `sponsor.ts` (3), `tracking.ts` (3), `doors.ts`, `capstone.ts`, `advisor.ts`, `activities.ts`. These are not previewable in `MailGallery.jsx` (which claims "كل رسالة كما تصل") and some keep the default footnote "إن لم تطلب هذه الرسالة فتجاهلها" on mails the user did not request (e.g. sponsor approval, `sponsor.ts:71-73`). Fix: register each in `MAIL_GALLERY` with sample data; pass an explicit `footnote`.

**M9 — RTL rendering (Low; unverifiable).**
`dir="rtl"` is set only on `<html>` (`mail.ts:63`); Gmail web/Android strip `<html>/<body>` attributes, so paragraphs render with bidi text but left alignment; `mailRows` and body cells set no `dir`/`align` (`42-44,74-77`). Fix: `dir="rtl"` and `align="right"` on the outer wrapper table/td and on each `<p>`; verify with Litmus/Email on Acid or a Gmail/Outlook.com test send from `MailGallery`.

**M10 — Tokenized links (Low).**
Sign-in: `/verify?e=<email>&t=<24-byte token>`, 15 min, one-time, atomic consume (`participant.ts:198,215-230`); coordinator identical (`coordinator.ts:51,73-76`); expert invite in the URL fragment, 7 days, one-time (`experts.ts:112-113`); rater 30 days (`impact.ts:266,289`); capstone sponsor `SPONSOR_DAYS` (`capstone.ts:274,348`); `?paid=` return carries nothing sensitive. The email address in the query string ends up in CDN/analytics logs. Fix: put `e` in the fragment or derive it from the token row.

**M11 — Domain authentication (unverifiable).**
`mail.ts:94` asserts SPF/DKIM/DMARC are set for `mail.sunkvalue.com`; nothing in the repo proves it. Owner checks: `dig +short TXT mail.sunkvalue.com` (expect `v=spf1 include:amazonses.com ~all`), `dig +short TXT resend._domainkey.mail.sunkvalue.com` (DKIM), `dig +short TXT _dmarc.sunkvalue.com` (expect `v=DMARC1; p=quarantine|reject; rua=mailto:…`), `dig +short MX mail.sunkvalue.com` (feedback MX), Resend dashboard → Domains → `mail.sunkvalue.com` = Verified, and that `RESEND_API_KEY` is a full-access key not restricted to another domain (the fallback in M7 suggests it once was). Also confirm the Resend plan and its daily/monthly limits (doc item 5).

**M12 — Demo account can receive reminder mail (Low).**
`reminders` filters only `status != suspended` (`admin.ts:919-923`); `demo.ts:15` uses a real-looking address; `sendMail` has no `is_demo` guard. Fix: `.eq('is_demo', false)` in all cron selects.

## 6. Legal / compliance (PDPL, consumer, e-invoicing)

**L1 — No consent or notice at sign-up (High).**
`SignIn.jsx` (email step `155-166`, name step `168-190`, Google confirm `191-201`) contains no privacy/terms link, checkbox or notice; no file under `leaders-app/src` references a policy (grep). PDPL (Royal Decree M/19, in force 2024) requires informing the data subject of purposes, recipients and rights before collection (Art. 12) and a lawful basis for disclosure to third parties (the employer/sponsor, Art. 15). Fix: a one-line notice + link on the name/Google steps ("بالمتابعة توافق على سياسة خصوصية برنامج القادة"), stored as `participants.consented_at` + version; a separate explicit consent when an org link is made (S2/L4).

**L2 — Policy pages do not describe this product (High).**
`home/privacy.html` lists Matrix data (strategic plan, demographic analysis, phone OTP, "AWS" for email, `144-180`) and none of: assessment answers and levels, CV uploads, audit IPs/UAs, Google sign-in, Resend, Creem (payment data, MoR), Cal.com/Calendly, sharing with sponsor organizations and their viewers, certificate public verification. `home/terms.html:170` prices the Matrix subscription; `home/refund.html:143-196` is a 14-day subscription refund; none are linked from the Paywall or sign-in. Fix: a Leaders-specific privacy notice, terms (one-time fee, Creem as seller of record, access revocation on refund/chargeback, certificate terms), and a refund page consistent with `payments.ts:155-161`; link them from `Paywall.jsx` and `SignIn.jsx`.

**L3 — Retention and erasure (Medium).**
No purge jobs for `email_challenges`/`coordinator_challenges`/`expert_challenges` (contain IPs), `auth_sessions`/`coordinator_sessions`/`expert_sessions` (IP + UA), `audit_log` (emails as actors, `doors.ts:165`), `certificate_checks` (IP + UA), private-bucket CVs/evidence. Participants cannot be deleted by admin: `ENTITIES` (`admin.ts:415-440`) has no `participants` entry and `remove` rejects other types (`822-826`); `privacy.html:191` promises full deletion. Fix: `admin.participant-erase` (anonymize PII, delete storage objects, revoke sessions, keep certificate serial + hash), and a monthly purge of challenges/sessions/checks older than 90 days inside `cron.reminders`.

**L4 — Sharing assessment outcomes with the sponsor (Medium).**
Defaults are conservative (`scores:false, contact:false`, `logic.js:717-721`) and cohort impact is suppressed under 5 (`coordinator.ts:160`), but with `scores` on, per-participant levels and named impact rows go to the employer (`coordinator.ts:124-135,163`, `OrgPortal.jsx:199,263`) with no recorded consent and only the widening notice (S2). Fix: block `scores` for participants without `org_share_consented_at`; show consent state in `org.visibility`; keep the transparency mail.

**L5 — Consumer-facing price and tax transparency (Medium; see P9).**
KSA E-Commerce Law/Regulations require the total price incl. VAT and clear refund terms at checkout; the Paywall shows neither.

**L6 — Audit and operational PII (Low).**
`wrongDoor`/`switchTo` write emails into `audit_log.actor` (`doors.ts:165`, `switch.ts:36`); the health report mails counts only — fine. Include `audit_log` in the retention policy.
