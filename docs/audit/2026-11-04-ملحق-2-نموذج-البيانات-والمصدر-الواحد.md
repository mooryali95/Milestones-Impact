## 2. The `.js` / `.ts` pattern in `leaders-api`

**Pattern (sound):** every `.js` file is pure, DB-free ESM logic (constants, cleaners, calculators) so Node/vitest and both React apps can import it; every `.ts` file is a Deno request handler that imports `db` from `core.ts` plus its `.js` twin (`capstone.ts:17`, `hall.ts:7`, `katon.ts:7`, `lab.ts:14`, `tracking.ts:11-14`, `final.ts:5`). `logic.js` (1,920 lines) is the hub and re-exports `journey/milestones/groups/continuous/final/katon/hall.js` (`logic.js:1913-1919`). `labels.js` is the label dictionary; `sponsor-match.js`, `groups.js`, `milestones.js`, `continuous.js`, `journey.js` are pure.

**Consumers:** 41 vitest files under `leaders-app/src` and `admin-app/src` import from the `.js` files; production UI imports too (`leaders-app/src/labels.js:1`, `App.jsx:12`, `DemoTour.jsx:8`, `screens/Capstone.jsx:13-14`, `screens/Profile.jsx:9`; `admin-app/src/leaders.js:24`, `handbook.js:6-7`, 17 admin screens). `leaders-app/src/single-source.test.js` greps the repo for copied labels/numbers — a good guard, but only for the patterns it lists.

**Checked for duplicated rules between a `.ts` and its `.js` twin** (`capstone`, `hall`, `katon`, `lab`, `tracking`, `final`): exports of the `.js` and the function list of the `.ts` are disjoint; the `.ts` files orchestrate only. No true twin duplication.

## 5. Migration hygiene

### 5.1 Idempotency
Excellent overall: every `create table/index` uses `if not exists`; every `add column` is guarded; `add constraint` is always preceded by `drop constraint if exists` or wrapped in `do $$ if not exists`; `create policy`/`create trigger` are preceded by `drop … if exists`; inserts use `on conflict` or `where not exists`; content updates are guarded by old-text equality or md5 (`20261102110000` uses 29 md5 checks). `20261022110000_multiple_owners.sql` and `20261102100100_leaders_activate_v5.sql` `raise exception` on unmet preconditions (good). Only nit: `20261104120000:70-75` grandfathers **all** non-demo participants at run time — re-running later grants new participants too (`on conflict do nothing` makes it idempotent but not time-safe).

### 5.2 Dependence on live data
Content migrations are conditional on current row text (`where q.text_ar = v.old_text`, `strpos(...) = 0`, md5 fingerprints) — correct for protecting admin edits, but rows skipped are invisible except in `20261102110000` (NOTICE). 20261103160000 edits Katon sentences only `where not exists answers` — if a participant answered first, production diverges from both JSON and migration with no record.

### 5.3 Same timestamp twice
`20261024150000_leaders_post_assessment.sql` and `20261024150000_leaders_verified_activities.sql` (both introduced in commit 24b27ac). They touch different objects (questions/raters/placement_model vs stage_requirements/reading/video/workshop/coaching) so order does not matter today, but tooling that keys on the timestamp (supabase CLI `migration list`, `db push`) will reject or merge them. Rename the second to `20261024151000`.

### 5.4 Down migrations
None. Rollback is manual via the 11 backup tables and `audit_log`. Destructive steps: `drop table` ×5 (20261030141000), `drop column signatories` (20261023170000), `drop column project_ar` (20261031150000), `drop constraint` on CHECK lists. Acceptable for a manually-applied setup if the backup tables are kept until sign-off and then dropped (#10).

### 5.5 Data mixed with schema
`20261024150000_post_assessment` (DDL + 3 inserts + 2 updates), `20261029120000_capstone` (DDL + 8 updates + 3 inserts + triggers), `20261104120000_payments` (DDL + env Creem product ids + grandfather), `20261104200000` (DDL + survey text), `20261022110000` (hard-coded owner e-mail), `20261024190000` (DDL + default program/cohort rows). Content-only migrations (handbook/questions/katon/tracks/text_fixes/journey_tokens) are ≈55% of the folder by count and ≈95% by bytes.

**Which is the source?** In practice three: the files are the authoring source, the DB is the runtime source **and** is editable from the admin panel (handbook editor, question editor, katon editor, model editor), and the generated migration is the bridge. Drift directions already observed: (a) DB edited after a migration → next migration skips the row silently (by design) and the JSON no longer describes production; (b) migration edited by hand (katon_false_v1) → JSON stale; (c) `baseline.sql` not regenerated → schema snapshot stale. There is no job that exports production content back into `supabase/content` (`scripts/tracks/build.mjs --snapshot` is the only, manual, reverse path).

**Recommendation (one source per content kind):** declare `supabase/content/*` the source, forbid admin edits to migrated content (or make admin edits write a JSON patch via an export endpoint), add `updated_at/updated_by/content_version` columns to content tables, and add a CI job: run all `verify*.mjs`, regenerate every generated migration and `git diff --exit-code`, run `snapshot.mjs --check`.
